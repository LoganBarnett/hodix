hodix is a set of Nix modules and configurations for running a self-contained IT
center.  It is meant for a household or a small business.

The name is short for hodos-nix.  "Hodos" is the Greek root for a way or a road.

* Vocabulary

- hodon :: A network that runs hodix.  Every hodon has a name.  One example is
  ~proton~.
- hodocule :: A network of hodons.  The [[*Roadmap][Roadmap]] says how hodons will join one.
- federated hodon :: A hodon in the same hodocule.  Both owners agree to it and
  both networks take part.
- visited hodon :: A venue one device uses while standing on it.  Home takes no
  part.
- hostname convention :: A themed pool of host names for a hodon to draw from.
  Nobody has to invent memorable names.  The periodic table is one convention.
  Kinds of wood, petaled flowers, and beans are others.

* Layout

Directory names say what a file is and where it works.

A directory of modules declares options.  Importing a module changes nothing
until its options are set.

A directory of profiles holds inert fragments.  A profile has no ~options~ or
~config~ attributes.  Importing a profile is what activates it.  nixpkgs uses
the same word for the predefined configurations under its ~profiles~ directory.

The prefix names the platform.  It is ~nixos~, ~darwin~, or ~home~ for Home
Manager.  The ~system~ prefix means the file works on NixOS and nix-darwin but
not Home Manager.  The ~agnostic~ prefix means the file works on all three.

* Facts

Facts are declared data about a hodon.  Other modules read them.  Facts set
almost nothing on a host themselves.

The facts are options under ~hodon~.  [[file:agnostic-modules/facts.nix]] declares
them.  Each option carries its own description.

** Declaring a hodon

A hodon's facts are an ordinary module.

#+begin_src nix :exports code
  {
    hodon = {
      name = "proton";
      networks.main = {
        vlanId = 10;
        ipv4.cidr = "10.10.0.0/24";
      };
      hosts.silicon = {
        system = "x86_64-linux";
        interfaces.main = {
          ipv4.address = "10.10.0.9";
          macAddresses = [ "b8:ca:3a:77:a9:2a" ];
        };
      };
    };
  }
#+end_src

An interface's name is a label and not the operating system's device name.  It
names the network the interface attaches to, so ~interfaces.main~ is the host's
attachment to ~networks.main~.  Set ~network~ on the interface when the two
names must differ.

** Using the facts

A flake needs the facts before any host exists.  Which hosts to build is itself
a fact.  And the facts themselves don't belong to any one host.  ~lib.mkHodon~
fills that gap.  It is called once per flake, never inside a host.

It evaluates the facts outside any host and returns three attributes:

1. ~hodon~ is the validated facts.  Reading it fails if any defect exists, and
   the failure lists every defect.  The flake enumerates hosts from it.
2. ~module~ carries the same definitions into a host.  Import it into every host
   so the facts appear there as ~config.hodon~.
3. ~forHost~ is ~module~ plus the identity of one host.  A host cannot tell
   which ~hodon.hosts~ entry is its own, so ~forHost "silicon"~ sets
   ~hodix.hostName~ for it.

#+begin_src nix :exports code
let
  hodonFacts = hodix.lib.mkHodon { modules = [ ./hodon.nix ]; };
  hostsOn =
    suffix:
    lib.filterAttrs (
      _: host: host.system != null && lib.hasSuffix suffix host.system
    ) hodonFacts.hodon.hosts;
in
{
  nixosConfigurations = lib.mapAttrs (
    name: _:
    nixpkgs.lib.nixosSystem {
      modules = [
        hodix.nixosModules.host
        (hodonFacts.forHost name)
        ./hosts/${name}.nix
      ];
    }
  ) (hostsOn "-linux");
  darwinConfigurations = lib.mapAttrs (
    name: _:
    nix-darwin.lib.darwinSystem {
      modules = [
        hodix.darwinModules.host
        (hodonFacts.forHost name)
        ./hosts/${name}.nix
      ];
    }
  ) (hostsOn "-darwin");
}
#+end_src

Inside a host, ~config.hodix.host~ is that host's own facts, so
~config.hodix.host.fqdn~ is ~silicon.proton.hodon.internal~ on silicon.  The
whole hodon is still there as ~config.hodon~.

~hodix.nixosModules.host~ and ~hodix.darwinModules.host~ apply the host's facts
to NixOS and nix-darwin.  Each sets ~networking.hostName~, ~networking.domain~,
and ~nixpkgs.hostPlatform~ as defaults, so a host can still override them.

Export ~hodonFacts.hodon~ as a flake output and scripts can read the same facts
with ~nix eval~.

** Internal domain

Every hodon uses the domain ~<name>.hodon.internal~.  The domain is derived from
the name and cannot be set.  Federation depends on every hodon sharing the
suffix.

** Hostname conventions

Importing a convention's profile selects it.

#+begin_src nix :exports code
{
  imports = [ hodix.agnosticProfiles.hostname-convention-wood ];
}
#+end_src

~hodon.hostnames.available~ then lists the names no host has taken.  Names are
handed out in pool order.  A pool lists its shortest names first and breaks ties
alphabetically, unless its theme carries an order of its own.  The periodic
table follows atomic number.

A convention is offered and not enforced.  Devices the hodon does not build keep
whatever names they have.

A hodon's own name sits one level beneath its convention.  It names something
the pool entries have in common and is never a pool entry itself, so no host can
take it.  Each convention suggests one.

1. ~periodic-table~ suggests ~proton~.  Every element is made of them.
2. ~wood~ suggests ~heartwood~.  A trunk has it at the core.
3. ~petal~ suggests ~nectar~.  Flowers offer it to their visitors.
4. ~bean~ suggests ~pod~.  Beans grow in one, and the hosts are the beans.

A custom convention sets ~hodon.hostnames.convention~ and ~hodon.hostnames.pool~
directly.

** Users and groups

Users name their groups, and a group names the groups it belongs to.  A group's
~members~ is derived from both, so membership has one source.
[[file:agnostic-modules/identity.nix]] declares these options.

#+begin_src nix :exports code
  {
    hodon = {
      users.ada = {
        fullName = "Ada Lovelace";
        groups = [
          "family"
          "nextcloud-admins"
        ];
      };
      groups = {
        family = { };
        nextcloud-admins.groups = [ "nextcloud-users" ];
        nextcloud-users = { };
      };
    };
  }
#+end_src

Here ~nextcloud-users.members~ holds ~ada~ through ~nextcloud-admins~.  Roles
build this way.  An admin group belongs to its user group, and nobody is listed
twice.

A group exists once it is declared under ~hodon.groups~.  Naming any other group
is a defect, so a typo fails at eval and not at login.  A group that leads back
to itself is a defect too.  Each group maps one to one onto a directory group
with ~members~ already flattened, so a directory that cannot nest groups loses
nothing.

** Hodocule

A hodon's facts hold its own view of the hodocule.  There is no central record.
Federation is pairwise and not transitive, so the hodocule is the set of peers
the hodon has shaken hands with.  [[file:agnostic-modules/hodocule.nix]] declares
these options.

A hodon publishes a card.  The card is the module a peer imports to add the
hodon to its hodocule, and it carries only what the hodon chose to publish.

#+begin_src nix :exports code
{
  hodon = {
    name = "proton";
    rootCertificate = builtins.readFile ./pki/root.pem;
    wireguard = {
      publicKey = "...";
      endpoint = "vpn.example.net:51820";
    };
    groups = {
      nextcloud-users = { };
      family.exported = true;
    };
  };
}
#+end_src

~hodix.lib.cardText hodonFacts.hodon~ renders the card as Nix source.  Export it
as a flake output and ~nix eval --raw~ writes the file to hand over.

The peer imports that file and the hodon appears under its
~hodon.hodocule.peers~.  Each entry is the peer's card plus what this hodon
decides about it.  Nothing is decided yet.  Grants will land here once identity
federation is designed.

1. ~rootCertificate~ is PEM text and not a path.  A card crosses repositories as
   one file.
2. ~wireguard.endpoint~ may be null on one side of a pair.  Both null is a
   defect, since neither side could open the link.
3. ~groups~ names the groups the peer attests membership for.  A grant by group
   may name only these.  On the home side, ~exported~ marks a group for the
   card.
4. ~hodon.hodocule.domains~ is the hodon's domain and every peer's.  A roaming
   device routes exactly these through its tunnel home.

** Validation

Invalid facts fail evaluation.  Option types reject malformed values.

Some defects span several facts.  Two hosts claiming one address is an example.
These are collected and reported together.  ~lib.mkHodon~ throws them.  Inside a
host they are assertions.

* Secrets

hodix keeps secrets with agenix and agenix-rekey.  A secret is encrypted to the
hodon's master identity and rekeyed to the SSH host key of each host that uses
it.  The generators from [[https://github.com/LoganBarnett/agenix-rekey-generators][agenix-rekey-generators]] create what can be created, so
a password or a key pair is declared and never typed.

The hodon declares three things.  [[file:agnostic-modules/secrets.nix]] holds the
first two and [[file:agnostic-modules/facts.nix]] the third.

1. ~hodix.secrets.directory~ is the directory of the repository that holds them.
   A hand-written secret is ~<name>.age~ inside it.  Generated secrets go under
   ~generated~ and each host's rekeyed copies under ~rekeyed/<host>~.
2. ~hodix.secrets.masterIdentities~ names the age identities that can open every
   secret.
3. ~hodon.hosts.<name>.sshHostKey~ is the host's ed25519 SSH host public key.
   Secrets for the host are encrypted to it, so a host without one can hold
   none.

#+begin_src nix :exports code
{
  hodix.secrets = {
    directory = ./secrets;
    masterIdentities = [
      {
        identity = ./secrets/master.age;
        pubkey = ./secrets/master.pub;
      }
    ];
  };
  hodon.hosts.silicon.sshHostKey = "ssh-ed25519 AAAA... root@silicon";
}
#+end_src

Hosts import ~hodix.nixosModules.secrets~ or ~hodix.darwinModules.secrets~.
[[file:system-modules/secrets.nix]] turns the settings above into agenix-rekey
configuration for the host.

The flake hands agenix-rekey the configurations so its commands can find every
secret, and the development shell carries the ~agenix~ command.

#+begin_src nix :exports code
{
  agenix-rekey = hodix.inputs.agenix-rekey.configure {
    userFlake = self;
    nixosConfigurations = self.nixosConfigurations;
    darwinConfigurations = self.darwinConfigurations or { };
  };
  devShells.default = pkgs.mkShell {
    packages = [ hodix.inputs.agenix-rekey.packages.${system}.default ];
  };
}
#+end_src

~agenix generate~ creates every generated secret and ~agenix rekey~ encrypts
each secret to the hosts that use it.  With ~ADD_TO_GIT=true~ in the
environment, ~agenix generate~ also adds to git the files a generator writes
beside a secret, such as a certificate.

* TLS

Every hodon has a root certificate.  Its services present certificates signed by
it, and every host trusts it.  The root is constrained to ~hodon.domain~, so a
stolen root key mints nothing outside the hodon.  [[file:agnostic-modules/tls.nix]]
declares the root's settings and [[file:system-modules/tls.nix]] issues and trusts.

Hosts import ~hodix.nixosModules.tls~ or ~hodix.darwinModules.tls~.  It brings
the secrets module with it.  The hodon sets the root's subject once.  The
organization defaults to the hodon's name.

#+begin_src nix :exports code
{
  hodix.tls.subject = {
    country = "US";
    state = "Oregon";
    locality = "Portland";
  };
}
#+end_src

The root is the generated secret ~root-ca~, so ~agenix generate~ writes its
certificate to ~generated/root-ca.crt~ under the secrets directory.  Its key
never leaves the repository.  Once that file exists, ~hodon.rootCertificate~
defaults to it, so the card and every host's trust store carry the same root.

A service declares the certificate it presents.

#+begin_src nix :exports code
{
  hodix.tls.certificates."ldap.proton.hodon.internal" = { };
}
#+end_src

The name must be under ~hodon.domain~.  The key is generated as a secret of the
host and the certificate is written beside it.  Certificates are short-lived, 47
days by the generator's default.  ~hodix.tls.certificateValidityDays~ changes
that for the hodon and a certificate's own ~validityDays~ for itself.
~config.hodix.tls.certificates.<name>~ then carries ~keyFile~, the key's path on
the host, and ~certificateFile~, the certificate in the repository.  Root alone
can read the key, so a service on NixOS reads it through ~LoadCredential~.

* Roadmap

[[file:docs/roadmap.org]] describes federation.  It covers how two hodons will form
a hodocule and reach each other's services without trusting new certificates.
The facts for it exist.  The link and the bridge do not.  It ends with the order
the first hodocule gets built in.
